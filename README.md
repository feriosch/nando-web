# nando-web

Web app for Nando: Bun, Vite, React, TypeScript, React Router and TanStack Query, served as a static build by nginx. Styled with Tailwind CSS v4 (`@tailwindcss/vite`), React Aria Components for interactive parts, `lucide-react` icons, and Zen Maru Gothic and Zen Kaku Gothic New self-hosted with Fontsource; body text is the system font, Japanese-ready. How screens are built: the `nando-design` skill (`.claude/skills/nando-design/`). Domain language: [`nando-server/GLOSSARY.md`](https://github.com/feriosch/nando-server/blob/main/GLOSSARY.md). Decisions: [`nando-server/docs/adr/`](https://github.com/feriosch/nando-server/tree/main/docs/adr).

## Layout

- `src/core`: Core.
  - `module.ts`: the types Core and Modules use to add to the shell: a **Home Card**, a **Settings Section**, and a `Module` (its name and `path` for its tab, its `theme` and `icon`, its own `routes`, plus its Home Cards and Settings Sections).
  - `shell/`: the bottom **tab bar** (Home, one tab per Module in `registry.ts` order, Settings; with more than 3 Modules the 4th tab is **More**, listing the rest at `/more`), **Home** (today's date in the Owner Time Zone, then every Home Card, Core's first, each drawing its own card in its contributor's theme) and the single **Settings** screen (every Settings Section, Core's first; a Module's section is tinted with its Module's theme: its header in the Module's accent after its icon, its grouped lists on the Module's surface with a hairline border; the app's version closes the screen). Each screen and the tab bar take the theme of the screen on view: its Module's, or Core's Paper. `createRoutes(registry)` builds all routes. `<LoadProblem>` is what a screen or card shows when it couldn't load: a message and "Try again". As on an iPhone, a newly opened screen (from a link or the tab bar) starts at its top, and going back returns to where it was scrolled: React Router's `<ScrollRestoration />`, in the shell. A back link to the screen this one was opened from goes back through history, as the back gesture does, so it too returns to where that screen was (`useCameFrom`, `ui/cameFrom.ts`); to any other screen, it opens that screen afresh. The shell records, for each screen opened from another, where it came from, and every `ScreenHeader` records its title, so a screen gives only its usual back link (`useBackLink({ to, label })`, such as a Word page's "Search"): opened from there or directly (from a Notification, a reload), it keeps that; opened from anywhere else, its back link goes there, named by that screen's title in its language ("‹ 期待", "‹ Backend Engineer"), or "Back" when that screen had none.
  - `ui/`: the shared building blocks every screen is made of: the large-title `ScreenHeader` (with an optional line over the title, such as a Word's reading), `SectionHeader` (an `h3` for a group within a Settings Section), `GroupedList` and `ListRow`, the bottom `Sheet`, `Button`, `Switch`, `SegmentedControl`, `Picker` and `PickerRow` (a value that opens the native picker when tapped), `saveFooter` (a form's saved message or problem under its list) and `Icon`.
  - `appearance/`: **Appearance** (System · Light · Dark, first in Settings → General), kept in this device's `localStorage` and applied to the whole page at once; System follows the device as it changes. A script in `index.html` applies it before first paint, so the screen never flashes the wrong colours.
  - `api/`: the API client. Every request is sent with `credentials: "include"` so the session cookie goes along; `get`, `post`, `put` and `delete` send and read JSON; `file` GETs a file as a `File` named from its `Content-Disposition`; a non-2xx response throws `ApiError` with its `status` and the server's plain-text message as `detail`. A `401` from any `/api/` route is also reported to `onUnauthorized` listeners, and the shell answers it by going to sign-in. `useLoadedSinceMount(query)` says whether a query has loaded since the screen opened, so a form starts from what the server has now, not a cached copy.
  - `identity/`: sign-in. `/sign-in` has the "Sign in with Face ID" button, and `/enroll` registers a new Passkey with an Enrollment Code from `nando-server enroll`. Either one starts a Session and opens Home. WebAuthn only ever starts from a tap. `passkeys.ts` wraps `navigator.credentials`.
  - `services.ts`: `useApi()`, `usePasskeys()`, `useShare()`, `useClipboard()` and `useLeave()`, which every screen, Core's and every Module's, uses to reach the API, the device's Passkeys, its share sheet (`share/share.ts`: files to the share sheet, or to the downloads where it takes none), its clipboard (`clipboard.ts`: copies text, such as a Suggested Reply), and other sites (`leave.ts`: leaves Nando for a URL, such as back to a Connector). `<CoreProvider>` provides them, so tests can pass fakes. It also holds `push` (`push.ts`), only to drop the Push Subscription a device may still hold from before Notifications moved to Telegram: once each time Nando opens, ignoring any failure.
  - `settings/`: Core's Settings Section ("General"): the Owner Time Zone, height (which Calories reads for the BMI) and the Gmail Digest. The Weigh-in reminder is Calories', set by its Assistant (the server's ADR 0012).
  - `days.ts` and `now.ts`: Days (YYYY-MM-DD in the Owner Time Zone) and `useNow()`, the time re-read every minute and on coming back to the app (the Day view uses it). `today.ts`: `useToday()`, today in the Owner Time Zone from the settings and `useNow()` (Home, the Day view, History, Weigh-ins and the Calories and Weight Home Cards use it). `weeks.ts`: weeks, named by the Monday they start on.
  - `connectors/`: **Connectors** ([ADR 0004](https://github.com/feriosch/nando-server/blob/main/docs/adr/0004-connectors-over-oauth.md)). The **consent page** at `/connect?request=<id>`, where the server's OAuth authorize sends the browser when the Owner adds Nando as a connector in an app such as Claude. Like `/sign-in` it has no tab bar, and it needs no Session, since on the iPhone it usually opens in a browser rather than the Home Screen app. It says who asks and what they get, as the server tells it what Core and each Module with Tools say they let a Connector do (`toolsDescriptions`), since Core doesn't know them ("**Claude** wants to use Nando. It will be able to search your Words and Kanji, and add, change, merge and delete your Words."; with none, "use every Tool Nando offers"), and the host it returns to. **Allow with Face ID** approves the request with a Passkey, starting WebAuthn only from the tap, and leaves for the URL the server returns, back to the app; **Don't allow** leaves for the server's deny URL. A cancelled Face ID or a refused Passkey stays on the page with the reason and both buttons; an unknown or expired request says so with no buttons. The **Connectors** Settings Section, after Notifications, lists each Connector with when it was approved and last used, in the Owner Time Zone ("Last used today", "Never used"); **Remove** asks first ("Claude will lose access to Nando until you connect it again."), then deletes it. With none, it says how to add one: a custom connector in the Claude app with the API's `/mcp` address.
  - `core.ts`: Core's own Home Cards and Settings Sections.
  - `version.ts`: the version at the foot of Settings (see **Version** under Deploy).
- `src/index.css`: Tailwind, the themes (Paper for Core, Kitchen wood for Calories, Ai-zome for Japanese) as CSS variables for light and dark, plain defaults for screens not restyled yet, and the View Transitions slide. Motion is off under `prefers-reduced-motion`.
- `src/modules/<module>`: one Module each (`calories`, `japanese`, `career`), exporting its `Module`.
  - `calories/`: what the Owner ate, read-only: the Calories Assistant logs Entries and saves Meals in Telegram, through the server's Tools, logs the weekly Weigh-ins, and sets the Daily Limit and the reminders (see the server's ADR 0008). The **Day view** at `/calories` (today in the Owner Time Zone, moving on at midnight; `?day=YYYY-MM-DD` for another Day, and a Day picker for today and the 7 Days before it) shows the Day's Entries, each with its Meal's emoji, Consumed Calories, Daily Limit and what's left. A Day with no Entries says to log what was eaten with the Calories Assistant in Telegram, or, in the future, that it hasn't started yet. **Meals** at `/calories/meals`: the Meals in use with their photo, kcal, store and Meal Tags, then the archived ones; a row opens nothing. A Meal's photo (`imageUrl`) is set by hand on the server and kept as it is. **History** at `/calories/history`, opened from the Day view: today and the 29 Days before it, newest first, each with its Consumed Calories against the Daily Limit that Day had (an Unlogged Day says "not logged", never 0 kcal), and "Show older" adds the 30 Days before; each Day opens in the Day view. The **Calories Home Card** shows today's Consumed Calories against the Daily Limit and opens the Day view. The **Weight Home Card** shows the latest Weigh-in, its BMI (or a link to set the height in Settings) and the change since the week before, and opens **Weigh-ins** at `/calories/weigh-ins`: every Weigh-in, newest first, read-only, as the Calories Assistant logs them (the server's ADR 0012). Calories has no Settings Section.
  - `japanese/`: the Owner's Words and Kanji, read-only (Claude adds and improves them through the Module's Tools; from Nando the Owner asks for that with a Word Request, see the server's ADR 0006). It has a tab and no Home Card, and its theme is **Ai-zome**: washi paper in indigo ink, with Calories' Zen Maru Gothic for display text and Zen Kaku Gothic New for Japanese display text. **Search** at `/japanese`: one search field, focused, that takes kanji, kana or Spanish (no romaji) and searches as the typing pauses; the Words found come first, each with its spelling, reading, Spanish meaning and Group (Basic, JLPT N3, N2 and N1 in green, blue, purple and red, easiest to hardest), then the Kanji, each with its character and meaning. An empty field shows a hint of what can be searched, and a search that finds nothing says so. Under the field, while there are any, the **Pending** strip lists the Owner's Word Requests, newest first (`Pending.tsx`): one waiting for a Claude run says "Waiting", one a run has taken "Claude is on it"; a done one shows Claude's summary and opens in a sheet with the summary, Claude's suggestions as things to do in Claude Code, and **Open word**, and opening it dismisses it; one Claude asks about shows the question with a button for each of its choices and **Other…** for the Owner's own words, and answering sends it back to waiting; a failed one says "Couldn't add" (or "Couldn't improve"), with why when Claude said, **Retry** and **Clear** (which dismisses it). A list that couldn't load says so, with "Try again", unless offline. The strip loads again whenever Japanese search opens and whenever Nando comes back to the foreground, never by polling; a Notification for a question or a failure opens `/japanese`, so the strip is where the Owner lands. A search that finds no Word offers **Add 「…」 with Claude**: a sheet with the text, which the Owner can change (conjugated or in kana is fine, as Claude adds its dictionary form), and the Group they found it in (Literature, Gaming, Anime, Movie, Miscellaneous or JLPT N1; the last one picked is kept in this device's `localStorage`). **Add** creates the Word Request (`POST /api/japanese/word-requests`) and closes the sheet, and the search then says Claude was asked, or, when an open Word Request already asks for the same, that it was already asked and is still waiting, or has a question for the Owner. A failed ask says why under the sheet's list, with the server's own reason if it gave one, and Add tries again. `wordRequests.ts` has the Word Request type and every Word Request hook: asking, listing, answering, retrying and dismissing; asking also reloads the Pending strip, so a new Word Request shows there at once. The **Word page** at `/japanese/words/<id>`: its reading over its spelling, its Spanish meaning, Word Tags written for display (`usually_kana` as "usually kana"), type, Group with its picture, notes and example sentences; its Word Links by kind (Synonyms, Antonyms, Related), each with the other Word, this side's note and Nuance Tags, opening the other Word; its Hints as plain text; and the Kanji in its spelling, each opening its Kanji page. At its foot, **Improve with Claude** creates an `improve` Word Request for it, then says Claude was asked (or already asked, still waiting); a failed ask says why, with "Try again". The **Kanji page** at `/japanese/kanji/<id>`: the character, large, its Spanish meaning, on and kun readings, Heisig numbers and story; its Components, where a stored Kanji opens its page and an irregular shape is shown by its keyword; and the Words spelled with it, each opening its Word page. The **Japanese Settings Section** has an **Anki** group with one row, **Export JLPT deck**: it fetches the JLPT deck (`GET /api/japanese/anki/jlpt.csv`, named from its `Content-Disposition`, such as `jlpt-2026-11-11.csv`) and hands it to the share sheet, for AnkiMobile, whose import screen comes up with the note type and deck set from the file's header; a device with no share sheet for files (a desktop) downloads it instead. The row says "Preparing…" while the deck is fetched, and a second tap does nothing. Safari opens the share sheet only within a tap, so if the fetch took too long for that, the row turns into "Share jlpt-….csv" for a second tap. Closing the share sheet is not a problem; a failed fetch says why under the list, with "Try again". Under the row: "In AnkiMobile, set Existing notes to Update.", so re-importing updates notes by their Id instead of adding them again.
  - `career/`: the Opportunities that Recruiters bring the Owner, read-only: Claude keeps them through the server's Tools, and the Owner changes things by talking to Claude. Its theme is **Slate**: cool bluish-gray paper, dark-gray ink and a professional blue, in the system font. `career.ts` has the types, mirroring the server's Career API. The **Career Home Card** has the Module's only control, the **Looking** switch, which saves at once (`PUT /api/career/settings`) and goes back, saying so, if that fails. Under it, "N Recruiters waiting" (hidden at 0) and the top 3 open Opportunities, each with its Company, role, Stage and next Step, opening `/career/opportunities/<id>`. With nothing to show it says "Nothing waiting." The whole card opens the **Career screen** at `/career`: **Waiting for you**, the Recruiters with a Suggested Reply that isn't late, newest first, each with their organisation, how long ago they wrote and the reply's first line ("Nobody is waiting." when empty); **Top Opportunities**, the top 5; and links to **All open (N)** at `/career/opportunities` and **Late Replies (N)**. Each Recruiter opens their **Recruiter page** at `/career/recruiters/<id>`: for each Conversation, its last 5 messages as bubbles, the Recruiter's on the left and the Owner's on the right, and its **Suggested Reply**, labelled when it is a follow-up or a Late Reply, with **Copy** (through Core's clipboard service, saying "Copied" for a moment) and **Open in LinkedIn** (the Conversation's URL, which the iPhone opens in the LinkedIn app), then **About your last message**: each note with what the Owner wrote, struck through, what is natural, and why. **Late Replies** at `/career/late` lists the Recruiters whose Suggested Reply is late, oldest message first. **Open Opportunities** at `/career/opportunities` lists every open Opportunity, top first. The **Opportunity page** at `/career/opportunities/<id>`, open or closed (a closed one shows how it ended, such as "Closed · Declined"): its role, Company, Stage and Interest; its **Steps** by date, the next one highlighted and past ones dimmed; **Pay and conditions**, each salary in 万円 with the yen under it ("900–1,200万円", "¥9,000,000 – ¥12,000,000"), the bonus, where the work is done, the office and the working language; its **Perks**, **Fit note** and **Details**; its **Recruiter**, opening their page; and the **Company Brief**. Only what is known is shown. Japanese text (names, Companies, messages) gets `lang="ja"`.
- `src/sw.ts`: the service worker's entry point.
- `src/registry.ts`: the only file that lists every Module. Core never imports a Module, and a Module imports only Core, never another Module.

UI strings are English only and kept simple so i18n can be layered on later.

## Run locally

Requires Bun. Start [`nando-server`](https://github.com/feriosch/nando-server) with `ALLOWED_ORIGINS=http://localhost:5173`, then:

```sh
bun install
bun run dev        # http://localhost:5173
```

| Env var             | Meaning |
| ------------------- | --- |
| `VITE_API_BASE_URL` | API origin, baked in at build time (default `http://localhost:8080` for `bun run dev`; required when building the image) |

## Test

```sh
bun run test       # Vitest + Testing Library
bun run e2e        # Playwright: the app in Chromium on an iPhone 17, against a fake API
bun run typecheck
bun run lint
```

`e2e/` is for what only a real browser shows, such as where a sheet lands when the keyboard is up; it starts its own Vite. The first time, run `bunx playwright install chromium`.

Every pull request runs these (with the Dockerfile's Bun and Node 22), and builds the container image (`.github/workflows/pr.yml`).

## PWA

Nando is installed from Safari's Share → Add to Home Screen and opens standalone. `vite-plugin-pwa` builds `manifest.webmanifest` and `sw.js` from `src/sw.ts`, and the iOS tags are in `index.html`.

- **Offline shell**: the build is precached and every navigation is answered with `index.html`, so the app opens without a connection. Font files are kept the first time a screen uses them (Zen Maru Gothic comes in many small unicode-range files, too many to precache). API calls are never cached; logging needs a connection.
- **Notifications**: Nando's Notifications come through Telegram, in each Assistant's chat (nando-server's [ADR 0008](https://github.com/feriosch/nando-server/blob/main/docs/adr/0008-assistants-on-telegram.md)), not as push messages: the app neither asks for the permission nor subscribes, and the service worker handles no push.
- **Icons**: `public/icon.svg` is the source: full-bleed (iOS rounds the corners) with its content inside the maskable safe zone. After changing it, run `bun run icons` to regenerate the PNGs and `favicon.ico` in `public/`, and commit them. The manifest's `theme_color` is Paper's accent `#8E4A49` and its `background_color` Paper's light background `#F6F4EF`.

## Container image

```sh
docker build --build-arg VITE_API_BASE_URL=https://api.<domain> -t nando-web .
docker run -p 8080:8080 nando-web
```

nginx listens on `PORT` (default `8080`; Cloud Run sets it). Unknown paths fall back to `index.html` so client-side routes work. `index.html`, `sw.js` and `manifest.webmanifest` are sent with `Cache-Control: no-cache`, and hashed files under `/assets/` are cached for a year.

## Deploy

Every push to `main` deploys to the `nando-web` Cloud Run service (`.github/workflows/deploy.yml`; also runnable by hand from the Actions tab). It signs in through Workload Identity Federation, builds the image with `VITE_API_BASE_URL=https://api.nanders.app` and `VITE_APP_BUILD` set to main's commit count, pushes it to Artifact Registry tagged with the commit, deploys it, and ends by checking that `https://web.nanders.app/` serves this build's `index.html`. Project, region, registry and deploy service account come from the repo variables `GCP_PROJECT_ID`, `GCP_REGION`, `GCP_AR_REPO`, `GCP_WIF_PROVIDER` and `GCP_DEPLOY_SA`.

If the new revision doesn't start, the deploy fails and traffic stays on the previous revision.

### Version

The foot of Settings shows the version, such as `Version 0.1.0 (45)`: `version` in `package.json`, then the build number, the number of commits on main when it was deployed. Every merge to main deploys, so the build number goes up by itself; bump `version` by hand for a release worth naming. Local and PR builds have no build number and show the version alone.
